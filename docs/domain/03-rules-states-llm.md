# 3. 규칙, 상태 전이, LLM이 들어갈 자리

> 2026-11-17 최신 반영: [중간 미팅 보고서](../interview/mid-meeting-report.md)에 맞춰 3-2의 MVP 상태 전이와 3-4의 LLM 경계를 정리했다. 3-1·3-3·3-5의 법령·플랫폼 자료는 기존 조사 기록이며 이번에 최신 법령·외부 정책을 재검증한 것은 아니다. 실제 MVP에서는 게시·종료·성과 입력이 수동이며, 초기 조사에서 다룬 일시정지·자동 집행·메시지 발송은 제외한다.

> 목표: 클라이언트가 "이 경우엔요?"라고 물을 지점을 우리가 먼저 찾는다. 세부 주제의 필수 조건 두 가지(상태 전이, LLM)가 이 도메인의 어디에 들어갈 수 있는지 찾는다.

## 3-1. 규칙 (최소 5개)

> 규칙은 '항상 / 절대 / ~이면 ~한다' 형태로 씁니다. 예외는 '그런데 만약 ~라면?'으로 찾습니다.
> 예: "배송중이 된 주문은 셀러가 취소할 수 없다" → 만약 고객이 배송중에 취소를 요청하면?

## 3-2. 핵심 대상과 상태 전이

핵심 대상은 마케팅 캠페인이다. 광고 한 건의 기획·초안·검수·사용자 승인·게시 기록·성과 평가를 묶는다. 정상 경로와 플랫폼 반려·취소 경로를 포함한다. 아래 표는 현재 MVP 기준이며 초기 자동 집행 가정은 [MVP 제외 범위](../decisions/mvp-scope.md)에 남긴다.

| 지금 상태 | 다음 상태 | 누가 바꾸나 | 조건 | 되돌림·경계 |
| --- | --- | --- | --- | --- |
| 기획중 | 초안 생성됨 | 사용자 요청·서버 | 필수 기획 입력과 선택 채널의 LLM 초안 생성 성공 | 자동 검수 요청 없음 |
| 초안 생성됨 | 검수 대기 | 사용자 요청·서버 | 문구 확인·수정 후 검수 요청 | LLM은 검수 자료 제공 |
| 검수 대기 | 검수 대기 | 사용자 요청·서버 | 경고가 있어 수정·재검수하거나 실패 후 재시도 | 경고만으로 수정 요청 전환 없음 |
| 검수 대기 | 승인됨 | 사용자 | 현재 문구의 검수 완료 후 직접 승인. 경고가 있어도 가능 | 승인 후 문구 변경·승인 취소는 현재 미지원 |
| 승인됨 | 게시 예약됨 | 사용자 | 미래 게시 시각·양수 예산·기간 저장 | 24시간 이내 일정은 경고 후 저장 |
| 게시 예약됨 | 집행중 | 사용자 | 플랫폼에 직접 게시한 사실 기록 | 예약 시각 자동 전환 없음 |
| 게시 예약됨 | 플랫폼 반려 | 사용자 | 반려 사유를 입력해 사실 기록 | 외부 API 미연동 |
| 플랫폼 반려 | 수정 요청 | 사용자 | ‘다시 고치기’ 선택 | 현재 예약 정보는 비우고 기존 사유·이력 보존 |
| 수정 요청 | 검수 대기 | 사용자 요청·서버 | 문구 수정 후 검수 요청 | 검수 완료 후 사용자 승인·재예약 |
| 집행중 | 종료 | 사용자 | 실제 종료를 기록 | 기간·예산 소진 자동 종료 없음 |
| 종료 | 성과 평가 완료 | 사용자 | 성과 입력·요약 준비 후 직접 완료 | 입력·요약 생성만으로 상태를 바꾸지 않음 |
| 기획중·초안 생성됨·게시 예약됨 | 취소 | 사용자 | 취소 요청 | 되돌림 불가. 늦게 도착한 LLM 결과는 저장 전 거절 |

`수정 요청`은 현재 플랫폼 반려 후 되돌림에 사용한다. `일시정지`와 승인 취소·예약 취소의 되돌림은 현재 MVP에서 제공하지 않는다. 기존 문자열 전용 캠페인은 기획중에서 직접 검수를 요청할 수 있는 호환 경로가 있다. 상세 허용 동작은 서버의 `allowed_actions`와 [API 계약](../../backend/README.md)을 따른다.

## 3-3. 시간에 따라 달라지는 규칙

> 아래는 초기 도메인 조사다. 현재 MVP는 메시지 발송·플랫폼 연동·전환 집계 확정을 하지 않는다. 일정이 저장 시각부터 24시간 이내(정확히 24시간 포함)이면 경고하되 저장을 허용하고, 과거 예약·미래 게시/종료·게시보다 이른 종료는 거절한다. 평가는 플랫폼 집계 기간 대신 사용자 입력과 요약 준비 여부를 기준으로 사용자가 완료한다.

## 3-4. LLM이 들어갈 자리

> **필수 조건입니다.** 세부 주제에는 LLM이 **서비스 기능 안에서** 쓰여야 합니다. 개발할 때 Claude를 쓰는 것은 여기에 해당하지 않습니다. 사용자가 서비스를 쓰는 동안 LLM이 무엇을 해 주는지 찾습니다.
>
> 좋은 자리를 고르는 기준:
> - 지금 사람이 **글을 읽고 쓰거나, 설명을 바꾸거나, 분류하는 데** 시간이 드는 곳 (2-2 As-Is의 문제 지점)
> - LLM이 틀려도 **사람이 확인하거나 규칙으로 걸러 낼 수 있는** 곳
> - 상태를 바꾸는 최종 결정은 **규칙이나 사람**이 하고, LLM은 초안·요약·분류·설명을 맡습니다
>
> 도메인별 예시:
>
> | 도메인 | LLM이 하는 일 | 사람이 확인하는 곳 |
> | --- | --- | --- |
> | 오픈마켓 셀러 운영 백오피스 | 고객 문의를 읽고 유형(취소·반품·배송 문의)을 분류하고 답변 초안 작성 | CS 담당이 고쳐서 보냄. 취소·반품 상태 변경은 규칙대로 |
> | 러닝 자세·훈련 코칭 | 러너가 남긴 훈련 기록과 느낌을 요약하고 다음 주 조정 제안 작성 | 코치가 승인해야 계획에 반영. 통증 언급은 의료 상담 권유로 |
