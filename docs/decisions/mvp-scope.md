## 포함 (8주 안에 반드시 동작 — 필수 스토리 전부, 취소·반려 스토리 포함)
| 스토리 | 기능 (F-__) | 왜 필수인가 |
| --- | --- | --- |
| US-01 캡션·해시태그 초안 받기 | F-01 | 광고 한 건 7시간 중 캡션 작성·수정이 4시간으로 가장 큰 부담이라 이것이 서비스의 출발점이다 (Q1) |
| US-02 초안 검수 요청하기 | F-03 | 초안 생성됨 → 검수 대기가 없으면 검수·승인 단계로 넘어갈 수 없다. 상태 4개 이상으로 이어지는 흐름의 연결 고리다 |
| US-03 위험 표현 확인하고 수정하기 (반려 경로) | F-02, F-03 | 필수 조건인 반려·되돌림 경로(검수 대기 → 수정 요청)이고, 고객이 요청한 표현 검수와 근거 자료 제시(Q2, 피드백 3)를 담는다. 위험 표현을 못 걸러 내면 R3~R5 위반 광고가 나간다 |
| US-04 게시 시각·예산 정하기 | F-04 | 승인됨 → 게시 예약됨 전이다. 게시 시각이 심사 24시간 여유보다 가까우면 알려 주는 규칙(3-3)이 여기에 붙는다 |
| US-05 성과 요약과 다음 광고 제안 받기 | F-05 | 고객이 '광고 수익 확인'을 새 필수 요구로 냈고(Q1), 이 요약이 다음 광고 초안에 들어가는 피드백 루프의 입력이다 |
| US-06 광고 취소하기 (취소 경로) | F-03 | 필수 조건인 취소 경로다. 집행 전 어느 단계에서든 사장님이 광고를 중단할 수 있어야 한다 (03 3-2) |

> **빠진 스토리 (확인 필요):** backlog.md에는 US-01~US-06만 있어서, 첫 데모 흐름에 들어가는 검수 대기 → 승인됨(F-02·F-03, R6)과 게시 예약됨 → 집행중(F-04, 사장님이 '게시함' 기록)이 스토리로 없다. 둘 다 5-2에서 필수 기능이므로 **제외가 아니라 스토리 미작성**이다. 집행중 → 종료, 게시 예약됨 → 플랫폼 반려(F-04)도 마찬가지다. 이 문서의 "포함"은 backlog 기준이므로, 스토리를 추가하면 이 표에도 옮긴다.

## 첫 데모(3주차)에서 보여줄 것
(user-flows.md의 흐름과 같아야 함)

광고 한 건(지난 광고: 10만원·7일, Q1)을 처음부터 끝까지 지나갑니다 (mvp-assumptions-questions 5-1, 5-2).

1. 상품·목표·채널·예산을 입력하면 캡션·해시태그 초안이 나온다 — 기획중 → 초안 생성됨 (F-01, LLM)
2. 초안을 고치고 검수를 요청한다 — 초안 생성됨 → 검수 대기 (F-03)
3. 위험 표현과 이유, 근거 자료, 고쳐 쓴 문장이 나오고 금지 표현이면 수정 요청으로 바뀐다 — 검수 대기 → 수정 요청 (F-02, LLM)
4. 고쳐서 다시 검수받고 사장님이 승인한다 — 수정 요청 → 검수 대기 → 승인됨 (F-02·F-03)
5. 게시 예정 시각을 정하고, 직접 올린 뒤 '게시함', 7일 뒤 '종료'를 기록한다 — 승인됨 → 게시 예약됨 → 집행중 → 종료 (F-04)
6. 성과 숫자를 입력하면 ROAS·수익 계산과 쉬운 말 요약, 다음 광고 제안이 나온다 — 종료 → 성과 평가 완료 (F-05, LLM)

취소(F-03)는 데모 흐름 밖의 별도 경로로 보여 줍니다.

> **user-flows.md와 불일치:** 현재 user-flows.md는 상태 이름이 03과 다르고(초안 검수 대기·초안 표현 검수·초안 승인됨), 5번 행에서 시스템이 플랫폼 광고를 개시하며 LLM이 관여한다고 적었다. 이 문서는 03·5-1·F-04 기준(사장님이 직접 게시하고 기록, LLM 없음)을 따랐다. 어느 쪽이 맞는지 팀이 정해 user-flows.md를 맞춰야 한다.

## 고객이 요청했으나 제외한 것
> `client-meeting-1.md`에서 '반영 안 함'으로 판정한 것 중 MVP와 관련된 것을 옮깁니다.

> client-meeting-1.md의 피드백 표에는 '추가 확인' 판정이 없다 (반영 1·2·3·4번 중 '반영 안 함'은 1번 하나). 그래서 아래는 '반영 안 함' 1건과, 고객이 요구한 것을 이번 MVP에서 일부 또는 조건부로 뺀 것을 함께 적었다. 둘째 줄부터는 미팅 기록에 판정이 없고 **우리가 정한 것**이다.

| 요청 | 제외 이유 | 다시 논의할 시점 |
| --- | --- | --- |
| 피드백 1: AI 논란 탐지의 기반 데이터를 업데이트할 때 사람이 컨펌하는 구조 ('반영 안 함') | 미팅 기록의 판정 이유 그대로: 검증에 사람 리소스가 너무 많이 들고, 탐지된 논란을 수정할지는 사용자가 선택하기 때문이다. MVP에서는 경고하고 수정 여부를 사용자가 정하는 흐름만 둔다 (H5 확인 대상) | 근거 자료 수집 범위(RAG, H10)를 정할 때. 고객이 다시 요청하면 그때 |
| '광고 수익 확인' (Q1 새 필수 요구) 중 **원가·수수료·배송비를 뺀 실제 이익** 계산 (F-07) | 수익 확인 자체는 F-05(필수)로 넣었다. 그러나 '수익'이 실제 이익인지 매출·ROAS인지 아직 모른다 (H3). 이익 계산에는 원가 입력이 필요해 F-05 뒤로 미뤘다. **고객이 필수로 말한 요구의 일부를 뺀 것이다** | 다음 미팅 질문 3번 답이 나온 직후. 실제 이익이라는 답이 나오면 F-07을 필수로 올리고 다른 선택 기능을 뺀다 |
| '광고 수익 확인' 중 **플랫폼에서 성과 자동으로 받아 오기** | 수동 입력으로도 수익 확인이 된다. 연동은 채널 미정(H2)과 API 확인 부족(H8)으로 8주 안에 위험하다. **고객이 필수로 말한 요구를 간소화한 것이다** | 채널이 확인되고 각 매체 API 조사가 끝난 뒤 (1~2주차 조사 결과로 판단) |
| 새 요구 '셀러별 개인화 AI' 중 매출·고객 데이터를 반영하는 부분 | 과거 광고 문구와 성과만 넣는 피드백 루프까지만 한다 (H9). 고객 데이터는 개인정보와 'LLM에 보내지 않을 정보' 문제가 있다 | 다음 미팅 질문 13번으로 입력 범위가 정해진 뒤 |
