# 백엔드 구현 결정 (2026-11-02)

> **2026-11-03 MVP 확장:** 아래 내용은 F-04를 먼저 구현했던 당시 기록입니다. 현재는 F-01~F-05 전체를 구현하며, 임시 수동 승인은 제거했습니다. 검수 성공 후 위험 표현은 경고로 보여주고 사용자가 승인 여부를 결정합니다. 최신 동작·API·기능별 브랜치는 [백엔드 README](../README.md)를 기준으로 합니다.

> **PostgreSQL 연결 추가:** 현재는 MySQL뿐 아니라 psycopg 기반 PostgreSQL·Supabase 연결도 지원합니다. PostgreSQL에서는 NullPool·prepared statement 비활성화를 적용하며 `/api/health/db`가 실제 SELECT 1로 연결을 점검합니다. 두 DB에서 같은 마이그레이션과 API를 사용합니다.

이 문서는 F-04 우선 구현에서 확정한 기술과 범위를 기록합니다. 현재 실행 방법과 API 사용법은 [백엔드 README](../README.md)를 따릅니다. 구현 코드·설정·테스트·실행 스크립트·배포용 의존성·문서는 모두 `backend/` 안에서 관리합니다.

## 기술과 인증

- 기존 제품 문서의 Supabase 대신 MySQL 8.4를 사용합니다. SQLAlchemy 2.x 동기 Session + PyMySQL + Alembic으로 연결·마이그레이션합니다.
- Docker Compose의 개발 DB와 테스트 DB는 서비스·볼륨을 분리합니다. MySQL 호스팅과 배포는 이번 구현 범위 밖입니다.
- 자체 JWT 인증은 PyJWT + pwdlib[argon2]를 사용합니다. Access Token은 15분 유효한 Bearer JWT이며 Refresh Token은 로그인부터 7일 유효한 HttpOnly 쿠키입니다.
- 로그인 세션과 Refresh Token 해시를 MySQL에서 관리하고 재발급 회전·재사용 감지·로그아웃 폐기를 적용합니다. 재발급에는 CSRF 헤더와 Origin 허용 목록을 검사하며 CORS는 기본 비활성화입니다.

## 기능과 상태

- `/api/v1/auth`: 회원가입·로그인·현재 사용자 조회(인증 검증)·재발급·로그아웃입니다.
- `/api/v1/campaigns`: 광고 문자열 등록·수정·수동 승인 및 US-04의 일정·예산과 US-07의 게시·종료·플랫폼 반려·다시 고치기를 구현합니다.
- 광고는 `content` 문자열 하나로 저장하고, 일정·예산도 캠페인 공통으로 둡니다. 채널별 일정은 추후 범위입니다.
- 수동 승인은 F-01~F-03의 AI 기능 없이 F-04에 진입하기 위한 임시 경로입니다. 기획중·수정 요청에서 승인됨으로 전환하며 AI 검수 통과를 의미하지 않습니다. 승인 후 문구 변경은 막습니다.
- 소유자 권한·시간 검증·허용 동작은 FastAPI가 판단합니다. 상태 변경과 이력을 같은 트랜잭션으로 저장하고 InnoDB 행 잠금으로 동시 변경을 직렬화합니다.
- 플랫폼 게시·종료·반려는 사용자의 수동 기록입니다. 일시정지·취소·자동 게시·자동 종료·LLM·성과 평가·프론트엔드·배포는 이번 범위에서 제외합니다.

## 기존 제품 문서와의 관계

- 전체 제품 요구사항은 저장소의 [백로그](../../docs/requirements/backlog.md)를 참고합니다. 제품 전체 MVP 범위와 이번 백엔드 구현 범위는 다릅니다.
- 백로그에는 US-07이 있고 검수 대기 → 승인됨도 US-03 인수 조건에 포함되어 있습니다. 기존 MVP 범위 문서의 ‘스토리가 없다’는 설명은 이전 기록입니다.
- 현재 구현의 DB·인증 선택과 임시 수동 승인 경로는 이 문서가 기록합니다. 기존 제품 문서와 루트 실행 파일은 이번 변경에서 수정하지 않습니다.
